Role Intelligence & What Google Really Wants

CRITICAL READ FIRST

Who is Mandiant?

Mandiant is a world-leading cybersecurity firm acquired by Google in 2022, now part of Google Cloud. They are famous for being the team that uncovered major nation-state attacks (APT1, SolarWinds response, etc.). The Red Team here is not a junior "scan-and-report" pen-test team — it is an elite group that emulates the most sophisticated real-world threat actors (APTs, ransomware groups, nation-states) to test enterprise and government clients at the highest possible level.

What this means for you: You are competing for a role where the bar is exceptional. Average knowledge is not enough. You need to demonstrate depth, practical ability, tool creation, and professional communication simultaneously.

Decoding the Job Description — Every Line Matters

Minimum: Offensive Certifications
OSCP is the floor, not the ceiling. OSCE3, OSEP, OSEE are highly valued. SANS GPEN, GWAPT, GXPN also count. Plan your cert path from Day 1.
3 Years: Security Tool Creation
This is a hard requirement. You must have written actual security tools — C2 payloads, scanners, exploits, automation scripts — not just used existing tools.

Network protocols, threat intel, sysadmin, project management, app development, incident response, code review, reverse engineering. You need demonstrated competency in at least four.
Client-Facing: Not Just Technical
You must write executive reports, present to C-level, scope engagements, manage client relationships. Technical brilliance without communication skill fails here.
Red & Purple Team
Red = attack the client covertly. Purple = collaborative — show defenders what attackers are doing in real-time. Both require deep understanding of detection engineering.
Threat Actor Intelligence
Mandiant is famous for threat intel. You must understand APT groups, their TTPs, MITRE ATT&CK framework, and how to emulate specific threat actors accurately.

Module 1A · Computer Networking (The Most Critical Foundation)

Every single security concept builds on networking. You cannot skip or rush this. Spend at least 10 full days on this topic.

OSI Model — Deep Understanding Required

L7 Application
HTTP/S, DNS, SMTP, FTP, SSH, SNMP, LDAP. Know how each protocol works byte-by-byte. Know what security issues exist at each.
L4 Transport
TCP 3-way handshake (SYN/SYN-ACK/ACK), TCP flags (RST, FIN, URG, PSH), UDP differences, port numbers, connection states.
L3 Network
IPv4/IPv6 subnetting, CIDR notation, routing (BGP basics), ICMP, NAT, ARP. Must be able to subnet in your head.
L2 Data Link
Ethernet frames, MAC addresses, VLANs, STP, ARP spoofing. Understand how switches vs routers work.

Active Directory (Critical for Red Team)

Active Directory is the backbone of enterprise environments. The majority of red team engagements involve AD. This is non-negotiable territory.

AD Authentication
Kerberos TGT/TGS flow, NTLM challenge/response, LDAP bind. Know the exact packets exchanged in each authentication method.
AD Attack Paths
Kerberoasting (SPN accounts), AS-REP Roasting (no preauth), Pass-the-Hash, Pass-the-Ticket, Overpass-the-Hash, DCSync, Golden/Silver Tickets, BloodHound attack paths.
AD Lateral Movement
PsExec, WMIexec, SMBexec, evil-WinRM, DCOM lateral movement. Know how each one works and what artifacts they leave on disk and in logs.
AD Persistence
Golden Ticket (krbtgt hash), Silver Ticket, Skeleton Key, ACL abuse (WriteDACL, GenericAll), AdminSDHolder, DSRM account.

C# / .NET (Required for Windows Tool Development)

Most modern offensive tooling targeting Windows environments (Cobalt Strike BOFs excluded) is written in C# because it runs in-memory via the CLR, has excellent Windows API access, and can evade many AV solutions. Learn C# well enough to write custom loaders, inject shellcode, and interact with Windows APIs.

C / C++ (For Exploit Development)

Buffer overflows, shellcode writing, custom kernel modules — these require C knowledge. Learn the basics: memory layout (stack/heap), pointers, memory management, Windows API calls via C.

PowerShell (Windows Offensive Scripting)

PowerShell is the native scripting language of Windows. Know how to: bypass AMSI, bypass execution policies, create reverse shells, enumerate AD, interact with COM objects, use Invoke-Expression and download-cradles.

Module 1D · Cryptography Basics

  • Symmetric encryption: AES (CBC vs CTR vs GCM modes), DES, 3DES — understand key sizes and attack surfaces
  • Asymmetric encryption: RSA (key generation, e/d/n, common attacks like small-e, padding oracle), ECC basics
  • Hashing: MD5, SHA-1, SHA-256, SHA-3 — understand collision resistance, preimage attacks, rainbow tables
  • TLS/SSL: full handshake flow, certificate chains, common vulns (BEAST, POODLE, HEARTBLEED)
  • Password hashing: NTLM, bcrypt, Argon2, salting — understand why plain MD5 is dangerous
  • PKI: CAs, certificate chains, CSRs, CRLs, OCSP — how certificates are used in real environments

Red Team Methodology & Operations

A Red Team engagement is fundamentally different from a pen test. The goal is not to find vulnerabilities — it is to test the organization's ability to detect and respond to a realistic adversary operating with specific objectives.

PHASE A
Planning & Scoping
Define objectives (reach Domain Admin? Exfiltrate specific data? Achieve physical access?). Define rules of engagement. Establish deconfliction process. Identify out-of-scope systems. Set timeline.
PHASE B
Threat Profile Selection
Which threat actor do you emulate? APT29 for a government client? FIN7 for a financial org? Select based on client's threat landscape. Map their TTPs to your attack plan using ATT&CK.
PHASE C
Infrastructure Setup
Redirectors, C2 servers (geographically distributed), domain fronting or CDN masking, malleable C2 profiles, OPSEC-hardened attacker infrastructure.
PHASE D
Initial Access
Phishing campaigns (pretexting, lure design), supply chain compromise scenarios, exposed services exploitation, physical access (tailgating, USB drops).
PHASE E
Exploitation & Escalation
Foothold → privilege escalation → lateral movement → domain compromise. Document every step for the report. Maintain OPSEC throughout.
PHASE F
Objective Achievement
Reach the crown jewels. Take a screenshot or exfil a small proof-of-concept file. This demonstrates real impact. Prepare for the debrief.

C2 OPSEC — Critical Concepts

  • Domain categorization and age — use domains categorized as business/finance, aged 6+ months, with clean Alexa ranking
  • Redirectors — Apache/Nginx mod_rewrite rules to redirect non-C2 traffic to legitimate sites, protecting C2 server IP
  • Malleable C2 profiles — make beacon traffic look like legitimate app (Slack, OneDrive, etc.) to avoid network detection
  • Sleep/jitter — randomize check-in intervals so traffic doesn't appear periodic (a key detection indicator)
  • Domain fronting — route traffic through trusted CDN (Cloudflare, Azure) to hide true C2 destination
  • Egress port selection — use 443 primarily, test other ports against client firewall; avoid outbound 4444 (too obvious)

AV/EDR Evasion Techniques

Modern endpoint security (CrowdStrike, SentinelOne, Microsoft Defender ATP, Carbon Black) uses behavioral analysis, memory scanning, and kernel-level hooks. Traditional obfuscation is not enough.

Process Injection
Classic (VirtualAllocEx/WriteProcessMemory/CreateRemoteThread), Process Hollowing, DLL Injection, Reflective DLL Injection, APC Injection, Thread Hijacking. Know the Windows APIs for each.
AMSI / ETW Bypass
Patch amsi.dll in memory (AmsiScanBuffer), ETW unhooking, syscall direct invocation to bypass userland hooks. Use SysWhispers for direct syscalls.
Living Off The Land (LOLBins)
Use legitimate Windows binaries for malicious purposes: certutil, mshta, wscript, regsvr32, rundll32, msiexec. These are trusted so AV doesn't alert.
Shellcode Obfuscation
XOR/AES encryption of payload, staged delivery (stager downloads full payload at runtime), indirect syscalls, custom PE loaders, position-independent shellcode.
BOF (Beacon Object Files)
Small C programs compiled as COFF objects, executed in-process within a Cobalt Strike beacon. Less noisy than spawning new processes. Know how to write and use BOFs.
Kernel Bypass
BYOVD (Bring Your Own Vulnerable Driver), kernel-mode rootkits, CI bypass. Advanced — required for the highest-level engagements. Know PPL bypasses.

Social Engineering & Phishing

Initial access in most real-world APT attacks starts with social engineering. You must know how to design and execute a realistic phishing campaign.

  • Pretexting: develop a convincing cover story (IT helpdesk, vendor, HR) tailored to target organization
  • Email infrastructure: SPF/DKIM/DMARC configuration for spoofing or lookalike domains, avoid spam filters
  • Lure design: Microsoft 365 credential harvest, DocuSign fake, HR policy update with malicious link
  • Phishing frameworks: GoPhish, EvilGinx2 (AiTM — bypasses MFA), Modlishka, Evilnginx
  • Spear phishing: LinkedIn OSINT for personalization, email timing analysis, CEO/CFO targeting for BEC
  • Vishing (voice phishing): scripting calls, pretexting as IT support, urgency creation techniques
  • MFA bypass techniques: SIM swapping awareness, AiTM proxy attacks, push notification fatigue

Report Writing — The Deliverable That Pays

CLIENT-FACING

Report Structure — Professional Pen Test / Red Team Report

A Mandiant report is a premium deliverable. The quality of your writing directly reflects on Google's reputation with enterprise clients. A badly written report can lose a client. Learn to write exceptionally well.

SECTION 1
Executive Summary
1-2 pages for the CEO/Board. Business language, no jargon. What was the overall risk level? What was the single most critical finding? What is the recommended priority action? Write this LAST.
SECTION 2
Scope & Methodology
What was tested, what was not tested, when, from which IP address, by whom. What methodology was followed (PTES, OWASP Testing Guide, CBEST framework, custom).
SECTION 3
Attack Narrative
Story of the engagement: how you got in, what you found, what you did. Written like a thriller but technical. This is what clients actually read and discuss in debriefs.
SECTION 4
Technical Findings
Each finding: severity (Critical/High/Medium/Low/Info), CVSSv3 score, affected system, description, evidence (screenshots with sensitive data masked), remediation steps, references.
SECTION 5
Remediation Roadmap
Prioritized table of all findings. Immediate (patch now), short-term (30 days), medium-term (90 days). Assigns ownership. Some clients turn this directly into JIRA tickets.
SECTION 6
Appendices
Full technical details, raw tool output, complete evidence. Security-sensitive — controls who receives this section. Raw Nmap output, screenshots, code snippets go here.

Finding Write-Up Template — Memorize This Structure

## Finding: SQL Injection in Login Portal (CRITICAL) CVSS Score: 9.8 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H) Affected Host: https://app.target.com/login Discovered: 2024-03-15 Description: The login form at /login is vulnerable to SQL injection via the 'username' parameter. An unauthenticated attacker can extract the contents of the user database, including hashed passwords, and bypass authentication entirely using a crafted payload. Evidence: Payload used: ' OR '1'='1' -- - Response: HTTP 200 OK, authenticated as admin user 'sysadmin' [Screenshot 1: Injected request in Burp Suite] [Screenshot 2: Response showing admin dashboard] Impact: An unauthenticated attacker can gain administrative access to the application and exfiltrate the customer database (estimated 2.3M records). Remediation: 1. Implement parameterized queries / prepared statements immediately 2. Deploy WAF rule blocking common SQLi payloads as temporary measure 3. Review all database interaction code for similar patterns 4. Implement application-layer input validation References: - CWE-89: Improper Neutralization of Special Elements in SQL Queries - OWASP Top 10 2021: A03 Injection

Report Writing Rules

  • Write clear, jargon-free executive summaries — pretend you're explaining to your non-technical parent
  • Every finding must have: description, evidence (screenshot), impact statement, specific remediation steps
  • Blur/mask sensitive data in screenshots (passwords, SSNs, personal data) before including in report
  • CVSSv3 score every finding — know how to calculate base score manually
  • Use consistent, professional language — no slang, no passive voice, no "we tried to do X" (say "we did X")
  • Practice writing reports for every lab machine you compromise — treat it as a real client report

Technical Interview Questions — Full Bank

INTERVIEW PREP

Networking & Protocol Questions

  • Q
    Explain what happens when you browse to https://google.comAnswer should cover: DNS resolution, TCP 3-way handshake, TLS 1.3 handshake (ClientHello, ServerHello, cert, key exchange), HTTP/2 GET request, response, rendering. Each step has security implications you should mention.
  • Q
    What is a "pass-the-hash" attack? How would you detect it?Answer: Windows NTLM authentication transmits a hash of the password. An attacker who captures the hash can use it directly without knowing the plaintext. Detection: anomalous authentication from new hosts, Event ID 4648, 4624 Type 3 from unusual sources, Sysmon Event 10 (process access to LSASS).
  • Q
    How does Kerberos work? What is Kerberoasting?Answer: AS-REQ→AS-REP (TGT), TGS-REQ→TGS-REP (service ticket). Kerberoasting: request service ticket for SPN account, extract ticket encrypted with service account's password hash, crack offline. Detection: Event 4769 with RC4 encryption type from unusual user.
  • Q
    What is DNS tunneling and how do you detect it?Answer: encoding data in DNS queries/responses (subdomain = data, TXT/NULL record = data). Detection: high volume of DNS queries per second, long DNS query names (>50 chars), queries to single domain, high entropy domain names, unusual record types (NULL, TXT at high frequency).
  • Q
    Explain SMB relay attacks. When do they work?Answer: NTLM authentication can be relayed. When SMB signing is disabled (default on workstations), capture NTLMv2 challenge with Responder, relay to target with ntlmrelayx. Works when: SMB signing disabled, target != source host, requester has local admin on target.

Web Application Questions

  • Q
    Walk me through exploiting a blind SQL injection vulnerabilityAnswer: Boolean-based: ' AND 1=1-- (true) vs ' AND 1=2-- (false) → different responses. Time-based: ' AND SLEEP(5)-- → response delays. Out-of-band: trigger DNS/HTTP request to your server. Automate with sqlmap --technique=B or manual. Exfil with SUBSTRING/ASCII.
  • Q
    How do you test for SSRF? What's the impact?Answer: Look for URL parameters, webhook URLs, import from URL features, image preview fetching. Test with: internal IPs (192.168.x.x), localhost, cloud metadata (169.254.169.254/latest/meta-data/iam/security-credentials). Impact: read cloud credentials → full cloud compromise, internal service access, port scanning internal network.
  • Q
    What is the difference between XSS and CSRF?Answer: XSS = attacker injects script that runs in victim's browser context (same origin). CSRF = attacker tricks victim's browser into making authenticated requests to target site. XSS can be used to bypass CSRF protections. CSRF mitigated by CSRF tokens, SameSite cookies. XSS requires input validation and output encoding.

Red Team Scenario Questions

  • Q
    "You've got initial access via phishing on a standard user workstation. Walk me through your next steps."Answer structure: (1) Situational awareness — whoami, hostname, ipconfig/arp, domain?, AV running? (2) Privilege escalation — check for SUID/sudo misconfig on Linux, SeImpersonate on Windows, common PE paths (3) Persistence — blend in, schedule task, registry runkey (4) Credential harvesting — LSASS, saved credentials, password manager (5) Lateral movement — identify targets via BloodHound/net commands (6) Domain compromise — Kerberoast, PtH, PtT to reach DC.
  • Q
    "Your beacon gets killed by the EDR within 10 minutes of execution. What do you do?"Answer: (1) Analyze why — memory signature? Behavior (LSASS access, process injection)? Network signature? (2) Adapt — switch to different execution method (LOLBin), modify malleable C2 profile, implement sleep/jitter, try process injection into trusted process (3) Reinfect — via different initial access vector or persistence already established (4) Change tooling — use different implant or BOF instead of full beacon.
  • Q
    "How do you emulate APT29 in a red team engagement?"Answer: (1) Read Mandiant APT29 report + ATT&CK page (2) Map TTPs to your attack plan: T1566.001 spear phishing, T1078 valid accounts, SUNBURST-like supply chain simulation, T1550.001 Application Access Token abuse, T1027 obfuscation (3) Use similar infrastructure OPSEC — cloud providers, legitimate domains (4) Custom malware mimicking their code patterns (5) Document every technique used and map to ATT&CK for the report.

Tool Development Questions

  • Q
    "Walk me through a security tool you built from scratch."This is your anchor question. Have ONE tool you know inside and out. Describe: what problem it solved, what language/libraries, key design decisions (why async vs threaded?), how you tested it, how you evaded detection with it, what you would improve.
  • Q
    "How would you write a shellcode loader in C# that evades AV?"Answer: Read shellcode (AES-encrypted on disk or remote), decrypt in memory, VirtualAlloc with RWX, copy shellcode, create thread (or use process injection). Evasion: delay execution (sleep), check for sandbox artifacts, indirect syscalls via SysWhispers to avoid userland hooks, sign the binary.

Behavioral Interviews — STAR Method Mastery

INTERVIEW PREP

The STAR Framework

S — Situation
Set the context. Be specific — real company (can anonymize), real project. What was at stake? Keep this to 2-3 sentences. The interviewer doesn't need the backstory of the company.
T — Task
What was YOUR specific responsibility? Distinguish between what the team did and what YOU did. "I was responsible for..." not "we were responsible for..."
A — Action
Specific steps YOU took. This is where 70% of your answer should be. Technical decisions, why you chose approach A over approach B, how you dealt with obstacles.
R — Result
What happened? Quantify if possible: "reduced attack surface by X%", "identified 12 critical vulnerabilities", "client implemented all recommendations within 30 days". What did you learn?

Essential STAR Stories — Prepare All of These

Question ThemeExample QuestionStory to Prepare
Technical Excellence"Tell me about a technically challenging security problem you solved."A complex exploit you developed, an evasion technique you created, a tool that solved a hard problem. Show depth of technical reasoning.
Failure & Learning"Tell me about a time you made a mistake that impacted your work."Be genuine. Show you take ownership, what you learned, what you changed. Google values intellectual honesty. Do NOT say "I can't think of a failure."

Communication Skills — The Overlooked Differentiator

CRITICAL

Speaking to Technical vs. Non-Technical Audiences

Mandiant consultants present to Fortune 500 CEOs. You must be able to switch registers — deep technical to executive-level — mid-conversation if needed.

The "Three Levels" Method

LEVEL 1
Executive (C-Level)
Business risk language. "An attacker could access your customer database, impacting 2M customers and costing $X in regulatory fines." No CVE numbers, no technical acronyms. Focus on: what can they steal? what operations can they disrupt? what is the cost?
LEVEL 2
Manager (CISO / VP)
Strategic language. "Your detection and response capabilities are insufficient — average dwell time in our test was 14 days before we triggered an alert." Focus on: gaps in security program, team capability, process improvements, budget priorities.
LEVEL 3
Technical (Sysadmin / Dev)
Full technical detail. "SMB signing is disabled on 47 workstations — here's the registry key to enable it, here's the group policy template, here's why NTLM relay works without it." They want specifics they can act on.

Active Listening in Technical Interviews

  • Repeat back the question in your own words before answering — confirms understanding and buys thinking time
  • Ask clarifying questions before assuming — "When you say 'web application', do you mean a black-box or white-box assessment?"
  • Say "I don't know, but here's how I'd figure it out" — never guess or make up answers
  • Structure long answers: "There are three main points here: first... second... third..." — prevents rambling
  • Slow down when speaking technical content — interviewers need time to follow complex technical reasoning

Public Speaking & Presentation Skills

Mandiant consultants present at security conferences (RSA, DEF CON, Black Hat). This is part of the job. Practice:

  • Present a technical topic to someone non-technical — record yourself and review
  • Create a "debrief" presentation for a simulated pen test and present it to a friend as if they're the CEO
  • Submit a CFP (Call for Papers) to a local security conference — the discipline of preparing a talk is invaluable
  • Join Toastmasters or similar if public speaking is a weakness — this is a legitimate career limiter at Mandiant

Common Mistakes — Avoid These

RISK MITIGATION

Technical Mistakes in the Interview

These mistakes will fail you immediately: Making up answers you don't know. Saying "I've used Metasploit" without knowing how it works internally. Claiming certifications you haven't earned. Overstating your tool development experience.
MistakeWhy It's FatalWhat to Do Instead
Answering with tool names only"I used Nmap" is not an answer. Everyone uses Nmap. Mandiant wants to know you understand what Nmap is doing.Explain the underlying protocol/mechanism: "Nmap SYN scan sends a SYN packet and analyzes the response — if SYN-ACK comes back, port is open. It never completes the handshake so it's stealthier and faster than connect scan."
Not knowing your own resumeIf you list OSCP, expect deep follow-up questions. If you list "Active Directory experience," expect detailed questions.For everything on your resume, prepare a 5-minute deep-dive answer. Reread your resume before every interview.
Ignoring the detection/blue team sideRed team at Mandiant is complementary to blue team. Not knowing detection methods shows incomplete understanding.For every attack you discuss, also explain how it's detected: which Event IDs, what network signatures, what EDR behavior alerts.
Skipping ethical and legal contextMandiant engineers interact with C-level clients. Ethics and legal authority are not optional — they're professional requirements.For any technical answer, acknowledge authorization, rules of engagement, legal considerations where relevant.
Rushing answers without structureA technically brilliant but disorganized answer signals poor communication skills — a key job requirement here.Pause, structure your answer ("There are three things to consider here..."), deliver clearly, then ask "does that fully answer your question?"

Preparation Mistakes

Over-relying on tutorials
Watching someone hack is not learning. You must DO it. For every video watched, spend 3x as long practicing the technique yourself in your lab.
Skipping the fundamentals
Jumping to "advanced" topics without solid networking/OS foundations. You'll hit a wall — every advanced technique requires foundation knowledge to understand and explain.
Never writing reports
The report is half the deliverable at Mandiant. Practice writing formal penetration test reports for every machine you compromise, not just the fun hacking part.
No original tool portfolio
The job requires 3 years of security tool creation. Using existing tools (Metasploit, Mimikatz) is not "tool creation." Build original projects, put them on GitHub with documentation.

Worst-Case Scenarios & How to Handle Them

CONTINGENCY

During the Interview

ScenarioResponse Strategy
You are asked a question you have no idea aboutSay: "I haven't worked with that specific technique yet, but based on what I know about [related area], I'd reason through it like this..." Then reason aloud. Intellectual honesty + structured thinking is valued over bluffing. End with: "Is that close? I'd love to understand the actual mechanism."
You freeze mid-answer on a technical questionPause and say: "Let me think through this systematically." Take 10 seconds. Structure: start from first principles. Start with what you KNOW about the topic, build from there. The interviewer has time — they'd rather see reasoning than speed.
The interviewer challenges your answer aggressivelyDo NOT back down immediately if you're confident. Say: "I understand the concern — my reasoning was [X]. Is there something specific about that approach you'd push back on?" Google interviewers sometimes challenge correct answers to test if you hold your ground. If they show you're wrong, acknowledge and update.
You can't think of a good STAR exampleBe honest about the scale. A small project where you showed the right behavior is better than a vague big story. Or say: "I haven't had exactly that situation, but here's a closely related one where I demonstrated the same principle..."
Technical audio/connection issues in virtual interviewTest everything 24 hours before: camera, microphone, internet speed. Have backup phone hotspot ready. If issues occur during interview, immediately email/call the recruiter — don't just sit in silence. Google recruiters are experienced with this.
You receive a rejectionEmail the recruiter within 24 hours. Ask specifically: "Are there areas of feedback that could help me improve for future applications?" Google has a 1-year reapplication policy — use the time to fill exactly the gaps they identified. Many successful Googlers applied 2-3 times.

During Preparation

Falling behind schedule
Don't try to catch up — reassess. Compress the non-critical sections. Prioritize: networking + AD attacks + tool portfolio + behavioral prep are the non-negotiables. Everything else adjusts.
Impostor syndrome
Normal and universal. The solution: small daily wins. Set concrete achievable goals (compromise this one machine today, finish this one script today). Progress compounds.
Lab environment breaking
Document your lab setup in a runbook so you can rebuild in 2 hours. Use snapshots in VMware. Store configs in Git. Treat lab maintenance as part of the job training.
Information overload
Stick to the plan phases. There's infinite security content to consume — you don't need all of it. Focus: complete your current phase before moving to the next. Depth beats breadth here.
